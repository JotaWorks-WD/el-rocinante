# El Rocinante Changelog

All notable changes to the El Rocinante parent theme are recorded here. Entries are newest-first. Dates are omitted for entries migrated from the style.css rolling block, which did not record them.

---

## [6.0.0] — 2026-08-02
Flip `respond()` to **mobile-first** and **rename its tiers to the network standard `sm`/`md`/`lg`/`xl`**: all four tiers are now `min-width`, `phone`/`tab-port`/`tab-land`/`big-desktop` become `sm`/`md`/`lg`/`xl`, and the parent's four `u-` utility call sites are inverted to mobile-base/desktop-enhanced. `abstracts/_mixins.scss` goes 1.0.0 to 2.0.0.

**MAJOR because `respond()` is part of the child-theme API surface and its meaning has inverted.** A block that previously *narrowed* a desktop base now *widens* a mobile base, which is close to the opposite. Read the next paragraph before planning any child work.

**The break is inert downstream. No child is affected by this release.** No child `@use`s the parent's Sass — each child Build repo is a separate compilation unit with no `loadPaths`, no `includePaths` and no symlink, so Sass constructs cannot cross the repo boundary at all. (CSS classes can and do, via the enqueued stylesheet; Sass cannot.) Fish Potrero and Coco ATV Tours each carry their own physical copy of `_mixins.scss` and keep compiling exactly as before. 360 Splendor has no copy, never calls `respond()`, and already writes mobile-first raw media queries.

A network crawl before this change counted **238 `respond()` occurrences: 234 call sites in Fish Potrero, 4 in this theme, 0 in Coco, 0 in RJK.** Coco's 9 hits are all inside comments and a placeholder mixin whose breakpoint names and values had already diverged completely from this one. So a major bump here touches **zero child sites**, and each child migrates on its own schedule.

**The one rule that cannot be relaxed:** within any repo, the mixin and its call sites must flip in the same commit. A flipped mixin with unflipped callers inverts every breakpoint on that site at once — there is no safe intermediate state.

### What changed

**Before** — `phone` / `tab-port` / `tab-land` were `max-width` 36/48/64em and only `big-desktop` was `min-width` 90em. The mixin **mixed directions inside itself**, the classic overlap-bug generator, and it was why any "from tablet up" rule had to be written as declare-then-reset: no upward tier existed below 90em. The two `-md` utilities did exactly that, and their own comment apologised for it.

**After** — `min-width` 36/48/64/90em as `sm`/`md`/`lg`/`xl`. Same `@if`/`@else if` structure, same `@error` on unknown names. The `xl` tier's value and direction are unchanged; it was already `min-width: 90em`.

### Why the rename shipped with the flip rather than after it

Device names were survivable under `max-width`, where `respond(phone)` genuinely meant "on phones". Under `min-width` the identical call means **"576px and up"** — nearly the opposite of how it reads, and a trap that gets more expensive with every call site added. `sm`/`md`/`lg`/`xl` carry no device claim and cannot be misread that way.

Doing it in the same release also converts a silent-wrong-behaviour failure into a build failure: every old tier name is now an unknown breakpoint, so a stale `respond(tab-port)` left anywhere hits the `@error` instead of quietly compiling against a flipped direction.

**The rename changes no CSS.** Values and directions are untouched — only the labels moved. Verified by diffing the pre-rename and post-rename compiles: byte-identical.

⚠ **Name collision to know about.** Coco ATV Tours' placeholder mixin already uses `lg`/`md`/`sm`, and they mean the opposite — `max-width`, in px, at 1199.98 / 991.98 / 767.98. So `respond(md)` now compiles in both repos and means "768px and up" here versus "991.98px and down" there. That file documents itself as an unverified guess made when the parent was unreachable, and it has zero real call sites, so replacing it wholesale is cheap today and gets more dangerous the longer the collision stands.

The four call sites in `base/_utilities.scss` all invert cleanly:

| Class | Before | After |
|---|---|---|
| `.u-row` | base `row` · `column` ≤48em | base `column` · `row` ≥48em |
| `.u-col-half` | base `50%` · `100%` ≤48em | base `100%` · `50%` ≥48em |
| `.u-justify-end-md` | base `flex-end` · `flex-start` ≤48em | base `flex-start` · `flex-end` ≥48em |
| `.u-text-right-md` | base `right` · `left` ≤48em | base `left` · `right` ≥48em |

**Rendered output is identical at every width except exactly 48em/768px.** Both the old `max-width` and the new `min-width` tiers are inclusive, so a viewport at precisely that width matched the small branch before and matches the large branch now — a one-pixel shift at one breakpoint, accepted deliberately. It is the same class of divergence already documented in `CLAUDE.md` §18.2 for the old mixin. Preserving it byte-exactly would need `min-width: 48.0625em`, which would put an off-number into every child migration that follows.

The base values on the two `-md` utilities are stated **explicitly** rather than left to their initial values, because `text-align` inherits and the old code explicitly forced `left` below the breakpoint — dropping it would let an ancestor's `center` leak through where it previously could not.

**Consequence for the child migrations.** With the names moved too, a child's migration is no longer a name-for-name mapping but a two-part rewrite per repo — invert the base/override relationship **and** rename the tier, in one commit. Fish Potrero is the bulk of it at 234 call sites: 130 `phone` → `sm`, 73 `tab-port` → `md`, 27 `tab-land` → `lg`, 4 `big-desktop` → `xl`. The compensation is that a half-done migration cannot ship silently — an un-renamed call is an unknown breakpoint and fails the build.

Compiled `dist/css/style.css` goes from 2,892 to 2,911 bytes, the growth being `.u-row`'s now-explicit `flex-direction: column` base. The four `@media (max-width: 48em)` blocks it previously emitted are now `@media (min-width: 48em)`, and **no `max-width` query remains anywhere in the parent's stylesheet**. `html { font-size: 62.5% }` is untouched and still flat, so the v4.0.0 root flatten is unaffected and children inheriting the root see no change.

SCSS only: no PHP, no JavaScript. Companion Build-repo commit carries the two SCSS sources. MAJOR: breaking change to a child-theme API surface, with a verified blast radius of zero on all three current children.

## [5.11.1] — 2026-07-30
Fix #12 REST gate that never fired in 5.11.0 (handler-methods shape mismatch); anonymous folder-taxonomy reads are now actually blocked.

**State of things during 5.11.0: the gate that release shipped did nothing at all.** Anonymous callers could still read the full folder tree at `/wp-json/wp/v2/roci_media_folder`, and the page and post trees with it, for the entire time 5.11.0 was live. Verified by `curl` before and after. The exposure itself is older than that release — it has existed since the three taxonomies were first registered with `show_in_rest => true`, because `public => false` does not restrict the REST API — so the honest summary is that **the hole was open continuously from the taxonomies' original registration through 5.11.0 inclusive**, and 5.11.1 is the first release that actually closes it.

The defect was one line, in the guard that decides whether a route handler is a read. It tested `empty( $handler['methods']['GET'] )`, which is only correct once WordPress has normalised a handler's methods into `array( 'GET' => true )`. At the `rest_endpoints` stage the value can still be the raw argument passed to `register_rest_route()` — the `WP_REST_Server::READABLE` constant, a plain string such as `'GET'`, or a comma string such as `'GET, POST'`. Indexing a string by `'GET'` does not evaluate the way the array form does, so the guard's `continue` fired for every handler on every route, nothing was ever wrapped, and the original permission callbacks were left exactly as core registered them.

What makes this worth recording rather than just fixing is **how** it failed: silently, and in the direction of appearing to work. Nothing errored, nothing warned, nothing logged. The filter ran, the loops ran, the routes matched, the function returned a complete endpoint array, and every visible sign said the gate was installed. Only the thing it was supposed to prevent still worked. That is the same failure shape as v5.10.3's overlay, where stripping a pseudo-element's colour left a transparent box still generating and still painting a band — source that reads correct, runtime that is not. The lesson both share: **a change whose whole purpose is to stop something must be verified by attempting the thing, not by reading the diff.**

5.11.1 normalises the detection across all three shapes: `stripos` for the string forms, and for arrays a check that accepts both `array( 'GET' => true )` and a plain list `array( 'GET', 'POST' )`, with anything else treated as not-a-read. Everything else in the gate is byte-identical and deliberately so — the capability is still checked before delegating to the original callback so single-term reads cannot leak term existence, writes are still untouched because only GET handlers are wrapped, the route boundary guard is unchanged, and `rest_base` is still derived from the taxonomy object rather than assumed from the slug. `show_in_rest` remains true; the route stays available to authenticated callers and to the block editor.

`taxonomies.php` goes 1.7.0 to 1.7.1. `folders.php` is untouched at 2.15.0 — the #6 remnant fix it carried in 5.11.0 was correct and unaffected, since that one changes registration args rather than filter behaviour and needed no runtime wrapping to take effect. PHP only: no JavaScript, no SCSS, no `dist` rebuild and no Build-repo counterpart. Closes bug #12, for real this time, and the acceptance test is the **anonymous single-term read** returning 401 rather than the collection route alone. PATCH: one guard normalised, no new API, no signature change, and no front-end rendering change on any site.

## [5.11.0] — 2026-07-30
Gate folder taxonomy REST reads behind `upload_files` (closes anonymous folder-tree exposure); child CPT folder taxonomies now register `public => false`. All three folder taxonomies register `show_in_rest => true` alongside `public => false`, and the second of those does not restrict the first. `public` governs front-end query and archive behaviour; REST read access is decided by `WP_REST_Terms_Controller`, which applies a capability test only when the request asks for `context=edit` and returns true for the default `context=view`. The practical effect was that anyone at all could read the entire folder tree at `/wp-json/wp/v2/roci_media_folder` without authenticating, along with the page and post folder trees. Confirmed live. `show_in_rest` stays TRUE and that is deliberate: withdrawing the route would also withdraw it from authenticated callers and from the block editor, which is a larger change than the problem needs. Instead a `rest_endpoints` filter in `inc/folders/taxonomies.php` wraps the READ permission callbacks on those routes to require `upload_files`, which is the honest question here — may this user touch media at all — covering administrators today and any future editor or author with media access while excluding subscribers. Four details in that filter are load-bearing rather than stylistic. The capability is checked BEFORE delegating to the original callback, because on the single-term route the original check can distinguish a nonexistent term from an existing one, so running it first would leak term existence to a caller not allowed to know. Only handlers whose methods include `GET` are wrapped, so create, update and delete keep the `manage_terms` and `edit_terms` checks core already applies — writes are untouched by construction rather than by intention. The route prefix is derived from the taxonomy object's `rest_base` rather than assumed from the slug, because `roci_register_folder_type()` merges arbitrary taxonomy args and a child could set one, which a hardcoded slug would silently fail to gate. And routes are matched by prefix with a boundary guard rather than by exact key, so the id route is covered without hardcoding core's ID regex while `/wp/v2/roci_post_folder` still cannot match a hypothetical `/wp/v2/roci_post_folders`. Two alternatives were rejected on evidence. The `rest_{$taxonomy}_query` filter runs after the permission check, so the best it could return is a 200 with an empty array, and it never fires for single-term reads — an anonymous caller could have walked the tree by ID while the collection route looked fixed, which is worse than not fixing it. Subclassing through `rest_controller_class` is the most idiomatic layer and remains the escalation path, but it means a new class and three registration edits for what one filter achieves, and it couples the theme to a core class signature that moves between releases. The gate is driven by a new public helper, `roci_get_folder_taxonomies()` in `inc/folders/folders.php`, which returns `roci_media_folder` plus every registry-registered CPT folder taxonomy — so any CPT a child opts in through `roci_register_folder_type()` is gated automatically with no per-taxonomy edit. That same merge expression is currently inlined at five other call sites in `counts.php`, `create.php` and `order.php`; those are deliberately left alone, and converging them is its own change. Nothing in this theme consumes these terms over REST — every folder data path is either `wp_localize_script()` or `admin-ajax.php`, and a nine-pattern grep across `inc/folders/` finds no REST touchpoint at all — so blocking anonymous reads removes no functionality the theme depends on.

Also in this release, the surviving half of bug #6: `roci_register_folder_type()`'s taxonomy defaults omitted `'public'` entirely, and `register_taxonomy()` defaults it to TRUE, so a CPT folder taxonomy registered through that path got a live front-end archive at its query var — strictly worse than the three explicit registrations, which were corrected to `public => false` in `taxonomies.php` v1.6.1 when this path was missed. `'public' => false` is now in those defaults.

**BEHAVIOUR CHANGE — read twice before deploying to a site with child folder CPTs.** Any child CPT folder taxonomy already registered through `roci_register_folder_type()` **loses its front-end archive** when this deploys. That is the intended #6 remnant fix rather than a side effect, and it is a change to the default args of a **public API**, not an internal one. Blast radius is **zero today** — neither current child registers a folder CPT, so nothing on any live site changes. A future child that wants the archive back must pass `'public' => true` explicitly through `$taxonomy_args`, which the merge already supports.

`taxonomies.php` goes 1.6.1 to 1.7.0, `folders.php` 2.14.0 to 2.15.0. PHP only: no JavaScript, no SCSS, no `dist` rebuild and no Build-repo counterpart. Closes bug #12 and the #6 remnant. MINOR: adds the public helper `roci_get_folder_taxonomies()` and changes the default args of `roci_register_folder_type()`; admin and API scope only, with no front-end rendering change on any site.

## [5.10.1] — 2026-07-30
Bulk Move panel now uses fixed positioning so it's no longer hidden behind the upload dropzone; dismisses on scroll/resize. With the upload dropzone open on `upload.php`, entering bulk-select mode and clicking Move opened the destination panel upward and behind the dropzone. Two mechanisms were stacked and only one was a bug. The upward flip was correct: `openMoveDropdown()` measures the space below the button and flips when there is not enough, and an open dropzone pushes the action bar far enough down the page to trip that test. The occlusion was the real defect, and it was not a z-index that lost a fair fight. The panel was `position: absolute` against `.roci-bulk-move-wrap`, which sits inside `.attachments-browser` in WP core's media-frame chain, so its `z-index: 10000` was resolved INSIDE an ancestor stacking context and never competed with the dropzone at all — a capped z-index cannot beat a sibling of the element that caps it, whatever value it carries. Devtools confirmed the panel rendering at its full 321px, painted underneath rather than clipped, which is what ruled out the overflow-ancestor explanation and selected this fix over the alternatives. The panel moves to `position: fixed`, which takes it out of that chain and resolves its z-index against the viewport, where 10000 wins. z-index is deliberately UNCHANGED rather than inflated: it has to clear core's dropzone layer and it has to stay below `.roci-modal-backdrop` at `100010`, or an open Move panel could paint over the bulk-delete confirmation dialog the Delete button in this same action bar raises. The node is NOT portaled to the document body — it stays inside the action bar, so the outside-click, Escape, Cancel and toggle handlers keep working untouched, since all of them test `moveDropdown.contains( e.target )`, which positioning does not affect. Because fixed offsets are viewport-relative, the static `top`/`right`/`bottom` in the SCSS are removed and `openMoveDropdown()` writes `top` and `left` inline on every open, computed from the button's `getBoundingClientRect()` with no scroll offset added, right-aligned to the button as `right: 0` previously achieved, and clamped so neither axis can run off screen. The `--above` modifier loses its CSS rule because a static offset would override the inline coordinate and re-break the upward case; the JS still toggles the class as a state marker and it stays useful in devtools, but nothing keys off it. Three latent defects in the flip logic are fixed as a consequence rather than separately. The threshold was a hardcoded `320` duplicating `max-height` from the SCSS with nothing linking the two, and being the maximum it flipped short panels that would have fitted; it now measures the panel's real `offsetHeight`. `window.innerHeight` was the wrong reference frame for an absolute panel inside the media frame's own scroll region and is the correct one now that the panel is fixed. And when neither side has room the panel now takes the roomier side instead of blindly flipping up into a space just as inadequate. Fixed panels do not travel with their button, so the panel dismisses on scroll and resize rather than repositioning — standard dropdown behaviour and cheaper than a reposition loop. The scroll listener is CAPTURED on `document`, because the media frame scrolls an inner container and scroll events do not bubble from an element to `window`, so a bubble-phase window listener would never fire. It explicitly ignores scrolls originating inside the panel: `.roci-bulk-move-list` is `overflow-y: auto` and a capturing listener sees its events too, so without that guard scrolling the folder list would have dismissed the panel — a worse bug than the one being fixed. ## [2.19.2] — 2026-07-08
Fix the root cause of the slug-meta corruption: added an `rwmb_roci_slug_value` save-time value filter. DB inspection confirmed MB Pro serializes the `roci_slug` field's config array into the `roci_slug` postmeta on REST/Gutenberg saves where the input is absent — the stored value was the `autocomplete…datalist…` config cruft. The v2.19.1 `is_string()` guard in `roci_save_slug_field()` only protected the `$_POST` read that syncs `post_name`; it could not stop the meta write, which happens inside MB Pro's own save pipeline before our `save_post` handler runs. The new filter fires at MB Pro's write point (`rwmb_{$field_id}_value`, before save) and rejects the non-string config-array fallback — returning the prior value, or empty — so the serialized config can never persist to meta. Filter signature verified against the Meta Box documentation. The display-time filter and the `is_string()` guard remain in place as defense in depth. See CLAUDE.md.

## [2.19.1] — 2026-07-08
Fix `roci_save_slug_field()`: the handler only guarded against `$_POST['roci_slug']` being unset, but on REST/Gutenberg/no-input save paths MB Pro substitutes the field's config array as the value — which passed the `isset()` check, was flattened by `sanitize_title()`, and wrote garbage (`autocompletefalsedatalist…`) into `post_name`. The guard now also requires `is_string()`, rejecting the config-array fallback before it can reach `sanitize_title()`. An empty string submission is treated as "no override intended" and leaves the existing `post_name` untouched. See CLAUDE.md.
