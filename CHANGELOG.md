# El Rocinante Changelog

All notable changes to the El Rocinante parent theme are recorded here. Entries are newest-first. Dates are omitted for entries migrated from the style.css rolling block, which did not record them.

---

## [5.9.1] — 2026-07-27
Move the Bulk Organize toolbar button from priority `-70` to `-65`, resolving a latent ordering collision in the media grid toolbar. Three views were claiming `-70` at once: WP core's own Bulk Select toggle, which `admin-folders.css` suppresses so Bulk Organize is the single bulk-mode entry point; the Fauxlder filter in `media-folder-filter.js`; and the Bulk Organize button in `folders-bulk.js`. Equal priorities are not ordered by anything declared. Core's `PriorityList.set()` walks the existing views and inserts before the first one of STRICTLY GREATER priority, so a tie falls through to the end of the list and the winner is whichever script called `set()` last — which in turn is whichever script wrapped `AttachmentsBrowser.createToolbar` last, since both files patch it by extending. That makes the rendered order a function of enqueue order rather than of intent, and it would flip silently the first time a dependency or a hook priority moved. `-65` is the smallest change that fixes it: greater than `-70` so the button lands to the right of the filter, which is the intended reading order of `[type -80] [date -75] [Fauxlder -70] [Bulk Organize]`, and still negative so it stays in the secondary toolbar list rather than jumping to the primary section on the right, which a positive value would have done. Worth being plain about what this does NOT do: nothing looks different on any screen today, because the two views never actually coexisted. On `upload.php` the Fauxlder filter is instantiated but never added to the toolbar — `media-folder-filter.js` suppresses it when the sidebar is present, since the sidebar already provides the filtering UI — and off `upload.php` `folders-bulk.js` is not enqueued at all, being scoped to that one screen. The collision was latent with a precise trigger: remove the sidebar from `upload.php`, or widen the bulk enqueue past it, and the two would land in the same toolbar with undefined relative order. This release closes that before it opens rather than after. One tie is deliberately left in place: the Fauxlder filter still shares `-70` with core's Bulk Select toggle, which is harmless by construction because that toggle is hidden by a `display: none` rule in `_admin-folders-bulk.scss`, so a tie against an invisible element has no visible outcome whichever way it resolves. Separating them would mean churning the `-70` slot the filter's own comments document in two places for no rendered gain; if that suppression is ever lifted, the layout needs revisiting anyway. `media-folder-filter.js` is untouched, and note that the per-option `filter.priority` added in v5.9.0 is a DIFFERENT priority system in a different file — that one orders `<option>` elements inside the select via Underscore's `sortBy`, this one orders views inside a toolbar via `PriorityList`. Same word, unrelated machinery; do not consolidate them. `folders-bulk.js` goes 1.4.2 to 1.4.3. No PHP, no SCSS, no build step — this `dist/js` file is hand-authored rather than compiled from the Build repo, whose Gulp pipeline outputs CSS only. The `style.css` bump is the delivery mechanism rather than ceremony here: Git Updater reads only that header to decide an update exists, and `roci_asset_version()`'s `filemtime()` cache-bust cannot fire until the file has actually reached the server. PATCH: one constant changed, no new API, and no rendering change on any screen that already worked.

## [5.9.0] — 2026-07-27
Render the `wp.media` modal Fauxlder filter alphabetically, matching the PHP sort v5.8.0 introduced, with "All Fauxlders" back at the top. v5.8.0 sorted the terms correctly and the two server-rendered choosers — the list-view filter and the New Fauxlder parent select — picked that up immediately, but the modal dropdown did not move at all. The cause was in `dist/js/folders/media-folder-filter.js` rather than in the sort. `buildFolderFilters()` re-keys the term array into a plain object keyed by numeric `term_id`, and core's `AttachmentFilters` builds its option list by mapping over that object (`wp-includes/js/media-views.js`). JavaScript enumerates integer-like own keys in ascending numeric order before any string key, so the PHP order was discarded before it ever reached the DOM: folders rendered in ascending `term_id`, which is creation order, and the `''` sentinel, being a string key, rendered LAST rather than first. Worth recording because it rewrites an earlier assumption — the order everyone had read as a deliberate drag arrangement was never `roci_folder_order` at all on this surface, it was creation order, and the PHP sort was being thrown away rather than never applied. The fix uses the ordering channel core already provides rather than fighting the key enumeration: `buildFolderFilters()` now stamps an incrementing `priority` on each entry as the PHP-sorted array is walked — the sentinel takes `1` so it pins to the top, folders take `2`, `3`, `4` and so on — and core's `sortBy('priority')` reproduces that sequence regardless of how the keys enumerate, because Underscore's `sortBy` is stable and ties break on original index. The counter starts at `1` and must never start at `0`: core reads `filter.priority || 50`, so a falsy `0` would silently become `50` and drop the sentinel into the middle of the folder list. Keys and `props` are deliberately untouched — `change()` looks up `this.filters` by the option value, which is the object key, and `select()` compares `filter.props` against the model with strict `===`, so `term_id` has to stay numeric and the sentinel has to stay keyed to the empty string for both round trips to keep working. Also adds a `render()` method to `RociMediaFolderFilter`, fixing a latent no-op found while tracing the above. Core's `AttachmentFilters` builds its option elements ONLY inside `initialize()` and defines no `render()` of its own, so the inherited `wp.Backbone.View.render()` did nothing here — there is no `template` for it to fill and the options were never registered as subviews for `views.detach()` to see — which made the `activeFilter.render()` call inside `rebuildFolderFilterSelect()` silent: `this.filters` was correctly refreshed after a folder was created or reordered and the visible select never repainted. The new method mirrors core's option-build block so the two paths cannot drift, builds its options with `document.createElement` rather than jQuery because this file's IIFE receives only `wp.media` and WP admin runs `jQuery.noConflict()` so there is no `$` in scope, and uses `textContent` rather than core's `.html()` because folder names arrive decoded from PHP per v5.7.0. It ends by calling `select()` to re-derive the active option from the model: replacing a `<select>`'s options resets it to the first entry, which would otherwise leave the control reading "All Fauxlders" while the model still held a folder filter and the grid stayed filtered on it. It deliberately does NOT re-run `listenTo()` — that model binding is made once in `initialize()`, and repeating it would fire `select()` twice on every change. One consequence worth knowing: because the reorder path now genuinely repaints, dragging folders in the sidebar re-renders the modal dropdown, still alphabetically since the payload is sorted, so the sidebar reorders and the dropdown does not follow it. That is the v5.8.0 split now actually enforced on both paths rather than only on first paint. The sidebar itself is untouched and keeps its `roci_folder_order` drag order. No PHP changed. Single theme-repo change with no build step: this `dist/js` file is hand-authored rather than compiled from the Build repo, whose Gulp pipeline outputs CSS only, and `roci_asset_version()` busts on `filemtime()` so the edit invalidates its own cache. `media-folder-filter.js` goes 1.7.5 to 1.8.0. MINOR: adds a `render()` method to the filter view; admin-only, with no front-end rendering change on any site.

## [5.8.0] — 2026-07-27
Sort the Fauxlder chooser dropdowns A-Z by the folder name the user actually sees, and leave the sidebar tree on its hand-sorted drag order. Three builders change — `roci_get_folder_terms_for_js()` and `roci_render_folder_select_dropdown()` in `inc/folders/filters.php`, `roci_build_folder_options_for_select()` in `inc/folders/create.php` — and between them they feed every folder `<select>` in the system: the `wp.media` modal filter, the Media Library and CPT list-view filters, the New Fauxlder modal's parent picker, and the AJAX rebuild of all of those after a create or a reorder. The split is deliberate rather than incidental. A sidebar is navigated, so a curated order earns its keep there; a select is used to find a folder whose name you already know, and hunting alphabetically through a hand-sorted list of forty folders is the case this release fixes. Adds `roci_sort_folder_children_alphabetically( &$children )` to `inc/folders/folders.php`, which `usort`s the contents of each sibling bucket in a `parent_id => WP_Term[]` map. Sorting happens in PHP and not through `get_terms( orderby => 'name' )`, because of the encoding v5.7.0 documented: WordPress stores term names HTML-encoded, so MySQL would sort `Logo &amp; Branding` by the literal characters of `&amp;` — filed under "a", nowhere near the `&` on screen. Only a PHP sort over `roci_folder_display_name()` orders by what is rendered. It is applied to the children map after bucketing and before the depth-first walk, not inside the walk, for two separate reasons: `roci_walk_folder_terms_depth_first()` is shared with `roci_get_folder_terms_with_depth()`, which feeds the bulk-organize Move dropdown and is out of scope for this release, and that walk emits each bucket in whatever order it is handed, so the map is the only place the order can be decided once. Hierarchy is preserved by construction — the sort reorders the CONTENTS of a bucket and never moves a term between buckets, so parents still nest their children and the depth and em-dash indentation are computed from the unchanged parent map exactly as before. Only sibling order within each level changes. The three builders also stop merging `roci_get_folder_order_query_args()` into their `get_terms()` call, which fixes a real defect rather than merely tidying: that helper sets a `meta_key`, and `meta_key` forces an INNER JOIN on `termmeta`, so any folder missing `roci_folder_order` was silently absent from all three choosers. Nothing guaranteed the meta existed, either — the lazy backfill `roci_maybe_initialize_folder_order()` is called only from `roci_get_folder_tree_html()`, never from the chooser path. Consequence worth knowing before upgrading: a folder that was invisible in these dropdowns will now appear in them. The helper itself is UNCHANGED and still serves the sidebar tree, the bulk Move dropdown and the new-term sibling lookup in `order.php`; only these three callers stop using it. The sidebar is untouched by construction and not merely by intent: it runs its own `get_terms()` and its own renderer, `roci_render_sidebar_tree_level()`, and after an AJAX create its refresh travels on the separate `tree_html` key produced by `roci_get_folder_tree_html()` — so the very response that resorts the selects alphabetically hands the sidebar back in drag order. `create.php`'s builder had to move in lockstep with the select renderer rather than being deferred, because it feeds the AJAX refresh of the same selects that renderer paints at page load: changing only one would have left a dropdown that visibly resorted itself the moment anyone created or reordered a folder. Comparison is `strnatcasecmp`, so case is ignored and "Fauxlder 2" precedes "Fauxlder 10" rather than following it. No JavaScript changed — `media-folder-filter.js` and `admin-folders.js` both iterate the array in the order they are given and neither sorts, so ordering the data server-side is sufficient, and no SCSS or `dist` rebuild is involved. `filters.php`'s walker docblock is corrected for its own accuracy: it asserted that the walk preserved a sort "already applied by get_terms (meta_value_num)", which this release makes false for one of its two callers. MINOR: adds the public helper `roci_sort_folder_children_alphabetically()`; admin-only, PHP-only, with no front-end rendering change on any site.

## [5.7.2] — 2026-07-27
Sit the Fauxlder media filter inline with core's type and date filters in the `wp.media` modal. v5.7.1 made the filter appear in every modal — a Meta Box media or image field on a Theme Settings page, the Insert Media dialog — but it rendered on its own second row and clipped under the modal scroll. All three selects were already siblings: WP's `Toolbar` routes any item with a negative priority into the secondary `PriorityList`, and core's type filter (`-80`), core's date filter (`-75`) and the Fauxlder filter (`-70`, `media-folder-filter.js:168`) therefore share one `.media-toolbar-secondary` container. Nothing was in the wrong place — the container simply had no inline layout outside the Media Library, because the rule that supplies it was written as `.upload-php .media-toolbar-secondary` when `upload.php` was the only screen that could reach it. Adds `.media-frame .media-toolbar-secondary { display: inline-flex; align-items: center }` to `Build/scss/admin/_folder-filter.scss`, above the existing block. `.media-frame` wraps every `wp.media` frame, the modal and the `upload.php` grid alike, so one rule covers both. Two details are load-bearing. The selector carries specificity 0,2,0, identical to the `.upload-php` rule it generalises: un-scoping to a bare `.media-toolbar-secondary` would have dropped it to 0,1,0, and any core rule sitting between those two weights would then have started winning on the one screen that already rendered correctly — a regression on the working case in the name of fixing the broken one. And `inline-flex` rather than `flex` because `flex-wrap` defaults to `nowrap` either way, which is what stops the third select dropping to a second row. The `.upload-php` block is left byte-identical and is now strictly redundant for grid mode; it is kept rather than folded in so this release cannot alter the Media Library, and can be collapsed later once the modal is confirmed. Media Library LIST mode is untouched by construction: it has no `wp.media` frame at all, its dropdown is rendered server-side by `roci_media_folder_filter_dropdown()` on `restrict_manage_posts` into `.wp-filter .alignleft.actions`, and no `.media-frame` ancestor exists for the new selector to match. Compiled `admin-folders.css` goes from 16,701 to 16,778 bytes; `style.css`, `admin-brand-scheme.css` and all eight page bundles recompiled byte-identical. PATCH: one CSS rule, no PHP, no JavaScript, no API change, and no rendering change on any screen that already looked right.

## [5.7.1] — 2026-07-27
The Fauxlder media-library folder filter now appears in every `wp.media` modal, including a Meta Box media or image field on a Theme Settings page, rather than only in the standard Media Library. The enqueue in `inc/folders/filters.php` tested `$hook_suffix` against a hardcoded array of `post.php`, `post-new.php` and `upload.php`, and that list could never cover the case it needed to: a Settings Page opens the same modal but its hook suffix is a generated `{parent}_page_{slug}` string, and because child themes register those pages under their own slugs there is no list the parent can maintain that would enumerate them. The gate is now `wp_script_is( 'media-views', 'enqueued' )`, which is true on exactly the screens where a media modal can be opened, whoever opened it, and needs no per-screen maintenance as children add pages. `media-views` is also this script's declared dependency, so the test doubles as a guarantee the dependency is genuinely present on the screen rather than being dragged in by us — the reason the gate is a test rather than a broad unconditional enqueue, which would have pulled `media-views` onto every admin screen through that same dependency. The `admin_enqueue_scripts` hook moves from the default priority to 15. The test can only read true after whoever owns the screen has called `wp_enqueue_media()`, which for both core and Meta Box happens at the default priority 10, so the previous registration was racing it; 15 clears that while staying below `branding.php`'s priority-20 callback, which gates on this same `roci-admin-folders` handle being enqueued. Priority 20 was rejected rather than overlooked — at equal priority the order would fall back to the `require` order in `folders.php`, an implicit dependency of exactly the kind this codebase documents against. Localize data, the `media-views` dependency and the style handle are unchanged; only the gate and the priority moved. `branding.php` is touched for its docblock alone, no executable line, because it asserted both the old screen list and "both enqueue callbacks run at the default priority 10" — a load-bearing ordering comment that this release makes false. Two consequences worth knowing: `admin-folders.css` now rides the same widened gate and loads on any screen with a media modal, harmless because its rules are scoped to `.upload-php` and to bulk and sidebar classes absent there, but a real payload increase; and the filter renders with core's toolbar styling rather than the theme's in a Settings-page modal, because `Build/scss/admin/_folder-filter.scss` scopes its layout rules to the `.upload-php` body class. That SCSS scope widening is deliberately deferred — it is a Build-repo change and this release is PHP-only. Also still tracked separately: the `priority: -70` ordering collision between the folder filter and the Bulk Organize button, and the bulk Move panel z-index. PATCH: enqueue condition widened, no new public API, and no behaviour change on any screen that already had the filter.

## [5.7.0] — 2026-07-27
Fix Fauxlders folder names rendering their ampersands as `&amp;amp;` wherever a folder name reached the screen. The cause was not in this theme's escaping but in an assumption about what `get_term()` returns. WordPress stores term names HTML-encoded: `wp_insert_term()` runs the name through `sanitize_term( …, 'db' )`, which fires the `pre_term_name` filters core registers in `wp-includes/default-filters.php` — `sanitize_text_field`, `wp_filter_kses`, and `_wp_specialchars` at priority 30 — so a folder an admin names "Rods & Reels" is written to `wp_terms.name` as `Rods &amp; Reels`, and `get_term()`/`get_terms()` hand that encoded string straight back because their default filter context is `raw`. Every read site then escaped an already-escaped value. Adds `roci_folder_display_name( $term_or_name )` to `inc/folders/folders.php` as the single decode-on-read chokepoint — `html_entity_decode` with `ENT_QUOTES` and UTF-8, accepting either a `WP_Term` or a bare stored name — and it is now the only `html_entity_decode` call anywhere in `inc/folders/`. `roci_format_folder_option_label()` decodes through it, which repairs its three callers at once: the list-view filter select, the grid-view Backbone localisation, and the option list rebuilt after an AJAX create. Those three deliberately do NOT call the accessor themselves; a second call would decode twice. Five direct `$term->name` reads are routed through it individually — the bulk Move dropdown's term data, the Add Media upload picker's folder list, the sidebar tree, and both move toasts. The two reported symptoms were the first two of those. Decoding happens in PHP rather than in the JS that renders it, for a reason worth recording: `wp_localize_script()` only `html_entity_decode()`s TOP-LEVEL SCALAR members of the array it is given and skips anything non-scalar, so folder arrays nested under `terms` and `folders` were never decoded on the way out, while sibling scalar labels in the same call were. No JavaScript changed — `textContent` and the picker's own `escapeHtml()` are already correct once they receive a decoded value, and moving the decode into JS would have split one rule across two languages. `create.php`'s parent-folder `wp_dropdown_categories()` is replaced by the existing `roci_render_folder_select_dropdown()`: core's `Walker_CategoryDropdown` re-escapes `$category->name` and can only be corrected through a global `list_cats` filter that would have to be attached and detached around this one call, so the last folder select in the system joins the theme's own renderer instead. Ordering is unchanged — that renderer uses `roci_get_folder_order_query_args()`, the same `meta_value_num` sort on `roci_folder_order` the old call passed by hand. Deliberate side effect: the parent dropdown now shows item counts and em-dash depth indentation from page load, which it already did the moment anyone created a folder, since `admin-folders.js` rebuilds it from `roci_build_folder_options_for_select()` and that source has always carried counts — this removes an inconsistency rather than introducing one. Escapes are preserved throughout: decode-then-escape is the required pair, and no `esc_html()` or `esc_attr()` was removed anywhere. In the sidebar the accessor was inserted INSIDE the existing `esc_html()` rather than in place of it, and the one escape that moved rather than stayed is the parent select's, which relocates from core's walker to the theme renderer's own `esc_html()`. The AJAX create response's term name is deliberately left encoded: it is not a display path, and its only consumer reads the parent id and never renders the name. Decoding cannot reintroduce markup, because `sanitize_text_field` runs `wp_strip_all_tags` before insert in both core's `pre_term_name` chain and this theme's own create handler, so only `&lt;` and `&gt;` from bare angle brackets survive as entities. MINOR: adds the public helper `roci_folder_display_name()`; admin-only, with no front-end rendering change on any site.

## [5.6.0] — 2026-07-26
Replace the Design tab's colour pickers with static locked swatches. Each of the seventeen colour fields now renders as a colour swatch, its hex in a monospace `<code>`, and a "Set in code" note where the palette supplies a value, or a dashed hatched swatch reading "Not set" where it does not — no input box, no picker, nothing editable anywhere on the tab. This finishes the direction v5.3.0 opened and v5.5.0 widened: brand is code-owned across the network, so the dashboard's job is to REPORT the brand rather than to own it. The per-field detection those two releases built is removed rather than refined — there is no longer a test asking whether this particular slot is code-supplied, because the answer is now the same for every slot, and a conditional that always resolves one way misrepresents where the decision actually lives. A dashboard-editable mode is a deliberate future per-client build, not a toggle hiding inside this loop. Display reads the palette, not the stored option: `roci_brand_palette()` seeds from `roci_design` and then applies the child filter, so the palette is the value every consumer actually resolves — the Fauxlders highlight, the Brand Colors scheme, both brand readers — and showing anything else would put a number on screen that nothing in the system uses. The two background keys sit outside the canonical fifteen and are absent from the palette entirely, so they fall back to the stored value rather than rendering permanently "not set". The `type="hidden"` input on every field is load-bearing and must not be removed. `roci_sanitize_design()` rebuilds `roci_design` from scratch on every save and writes an empty string for any key absent from the POST, and its return replaces the stored row wholesale. This tab also carries six editable non-colour fields — the two font families, base font size, header style, sticky header and button style — sharing one form and one Save button, so an admin who changes a font and saves triggers a full `roci_design` write while every colour field is static. Without a submitting input for each colour key that save would wipe all seventeen stored colours, silently, and the swatches would keep displaying the filter's colours afterwards so nothing on screen would look wrong. The input is `hidden` rather than the `readonly` text field v5.3.0 used, because a readonly input still renders the empty box this presentation exists to remove, and it carries the STORED value rather than the displayed one — persisting the palette value would freeze a copy into the option that then drifts as the child's filter moves on, which is precisely the two-sources problem the palette resolver exists to prevent. The swatch value is gated through `sanitize_hex_color()` before interpolation, which returns null for anything that is not a bare hex. That gate is display-only and deliberately strict: `esc_attr()` keeps a value inside the style attribute but passes ';' and ':' through, so an unvalidated palette value could inject further CSS declarations. A filter returning `rgb()`, a named colour or a `var()` therefore renders as "not set" on this tab while continuing to work everywhere else — a display limitation accepted deliberately, and never applied to the stored value. The swatch border is unconditional because `color-white` is `#ffffff` against a white admin background and would otherwise render as nothing at all. The `wpColorPicker()` initialisation is removed from `dist/js/theme-settings.js`, where it now matched zero elements since no `.roci-color-picker` input remains. The `wp-color-picker` dependency on the `roci-settings-js` enqueue is deliberately RETAINED: that enqueue is shared by all seven settings tabs, including the Identity tab's media and logo uploader, and dropping a dependency to save a few kilobytes on admin screens alone would risk a working cross-tab feature for no gain. MINOR: presentational for the Design tab only, with no change to stored data and no rendering change on any site.

## [5.5.0] — 2026-07-26
Widen the Design-tab mirror policy to code-owns. A colour field is now a read-only mirror whenever `roci_brand_palette()` supplies a value, not only when the stored value is empty. The narrower test it replaces left a field editable when a stored value AND a code-supplied value both existed, which was a lie: `roci_brand_palette()` applies the child filter last, so the filter value is what every consumer actually reads — the Fauxlders highlight, the Brand Colors scheme, and both brand readers. The dashboard displayed an editable colour that nothing in the system used; an admin could edit it, save it, and see no effect anywhere, silently and with no explanation. Locking the field whenever the palette disagrees with what is stored makes the display honest: if the colour is supplied in code, the dashboard does not own it and no longer pretends to. The test is "differs from, or fills" rather than the simpler "palette is non-empty", and that distinction is load-bearing — `roci_brand_palette()` SEEDS from the same `roci_design` option before applying the filter, so on a site with no filter registered the palette always equals the stored value. Locking on non-empty alone would therefore have made every saved field read-only on an ordinary dashboard-managed site: write once, then never editable again without database surgery. Requiring disagreement keeps those sites fully editable while still catching every code-supplied value, because a filter that supplies a colour necessarily makes the palette differ from what is stored, or fills a slot that was empty. The one case left editable is a stored value the palette exactly equals, which is harmless — it is indistinguishable from an unfiltered site, and if a filter really did assert that same value the next save simply reasserts it. A known cosmetic remains in that case: `data-default-color` carries the same hex as `value`, so wp-color-picker's Default button resets to the colour already shown — a dead control, deliberately left rather than fixed by locking the field. Also corrects the `roci_brand_palette()` docblock, whose `@return` still described an eleven-key map after v5.4.0 made it fifteen. Fish Potrero's own fill of the canonical interface lands in the child repos, not here. MINOR: behavioural for the Design tab only, no rendering change on any site.

## [5.4.0] — 2026-07-26
Standardize a fixed canonical colour interface across the network. Fifteen `$color-*` Sass variables — primary and its four tonal steps, secondary and its two, tertiary and tertiary-accent, accent, eyebrow, white, black and grey — are now declared by every repo whether or not that repo consumes them: the parent ships defaults and a child fills the slots its brand needs from its own palette. The parent gains the ten it was missing, purely additively — the seven unfilled brand slots carry `#333` with an "update on child" note, `$color-grey` carries a real `#999`, and the two that shadow existing consumers carry their current resolved values, `$color-accent` `#000` and `$color-eyebrow` `#777`, so repointing `--color-accent` off `$color-secondary` and `--color-eyebrow` off `$color-grey-dark` in `base/_tokens.scss` is byte-neutral. Compiled `dist/css/style.css` is unchanged at 2,892 bytes, verified byte-for-byte rather than by length. `--color-text` keeps reading `$color-grey-dark` and must continue to: it and `--color-eyebrow` happened to share `#777`, so wiring both to one variable would have compiled identically today and detonated later on any child that filled `$color-eyebrow`, silently recolouring its body text. The Phase 6 retirement note is reframed rather than deleted — `$color-primary-light`, `$color-secondary-light` and `$color-secondary-dark` return not as parent internals but as interface slots, and being unreferenced in the parent is now the expected state for most of the fifteen rather than evidence of dead code; `$default-font-size` stays retired. On the PHP side the Design tab's `roci_design` keys are renamed to the hyphenated canonical spelling so the picker vocabulary and the SCSS interface are one set rather than two needing translation: fifteen canonical keys plus `background` and `background-alt` as parent-only extras the canonical vocabulary does not cover, seventeen pickers in total, with the tab's key list and `roci_sanitize_design()`'s field list kept in sync because the sanitiser rebuilds the option from scratch and blanks anything it does not list. A migration on the `option_roci_design` filter carries legacy underscore keys forward on read — non-destructive, so the stored row is never rewritten and no half-migrated state can exist — with the canonical key winning if both spellings coexist. The old `primary_accent` and `secondary_accent` keys are deliberately dropped rather than mapped: the canonical vocabulary expresses variation tonally and has no unqualified "accent of primary" concept, so there is nowhere truthful to put them, and mapping them onto `-light` would reassign a value chosen for one meaning to a slot that means another. All four brand readers — `roci_admin_brand_accent`, `roci_has_brand_accent`, `roci_brand_palette` and `roci_admin_brand_secondary` — move to the hyphenated keys. MINOR: additive and structural, with no rendering change on any site.

## [5.3.0] — 2026-07-26
Introduce `roci_brand_palette()` as the canonical brand store and route the existing readers through it. The eleven Design-tab colour keys resolve in one place — default source the `roci_design` option, overridable in code through the `roci_brand_palette` filter — and `roci_admin_brand_accent()` and `roci_has_brand_accent()` now read that resolver rather than the option directly, each keeping its own filter as the final say so anything already hooking them is unaffected. This collapses three brand filters toward one source and repairs a real trap shipped at v5.2.0: a child supplying its brand through the accent filter alone had a genuine brand, an empty option row, and a predicate that answered "no brand", so its admin scheme silently never registered and the child had to know to register a second filter as well. The Brand Colors scheme becomes two-coloured. Primary drives the structural surfaces — the current `#adminmenu` item and `#wpadminbar` — through a new `--roci-brand-structural` custom property, and Secondary drives the highlight surfaces — links, `.button-primary` and form-field `:focus` — through `--roci-brand-accent`, which keeps its name while its source moves from Primary to Secondary so every existing consumer in the stylesheet resolves unchanged. The lightened legibility mix moves with the surfaces it protects, from `$accent-light` to `$structural-light`: it exists because a dark brand is illegible on WP's `#1d2327` chrome, so leaving it on the accent property would have silently detached the guard from the colour it guards. Both properties carry their own `#2271b1` fallback, since an unresolved custom property invalidates its entire declaration rather than reverting. A new `roci_offer_brand_scheme` filter separates "a brand exists" from "offer the scheme", so a child can brand its Fauxlders folders in code without a new option appearing in every administrator's profile; it defaults to `roci_has_brand_accent()` so the common case stays zero-config. The Design tab's eleven colour pickers now mirror the palette read-only for any slot supplied in code: the mirrored value is written to `data-default-color` and never to `value`, the field is `readonly` rather than `disabled`, and wp-color-picker initialisation is skipped for those fields because it would otherwise rebuild live controls around the input regardless of the attribute. That combination is load-bearing rather than stylistic — `roci_sanitize_design()` rebuilds the option from scratch on every save and writes an empty string for any key absent from the POST, so a disabled or omitted field would have wiped all eleven stored colours the next time anyone saved the tab, including a save that touched only the font settings. The sanitiser is deliberately unmodified. The menu icon `current` slot stays `#fff` rather than taking Primary, because it sits on a Primary-coloured background and would otherwise vanish into it. MINOR: additive, backward-compatible in both directions, and no existing behaviour changes.
